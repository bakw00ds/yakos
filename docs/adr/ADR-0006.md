# ADR-0006: Node Agent-SDK sidecar for answerable structured questions

**Status:** Accepted (operator-approved 2026-06-17)
**Date:** 2026-06-17
**Deciders:** operator — approved the Node sidecar model, opt-in flag, and security posture
**Refs:** `internal/consoleui/chat_handler.go`, `internal/serve/serve.go`,
`internal/dispatch/stream.go`, ADR-0005 (hybrid auth)

---

## Context

The yakOS console's Chat pane supports interactive multi-turn sessions.
Agents can call `AskUserQuestion` to block execution and ask the operator
for structured input (one of several provided options, with optional free-
form notes). Before v0.45.0.0, the SSE stream emitted an `ask_user_question`
frame, but the console had no answering mechanism: operators had to read the
question from the stream and type an answer back at the terminal, breaking the
in-browser workflow.

Two constraints shape the solution:

1. **The existing CLI engine cannot answer `AskUserQuestion`.** The yakOS
   dispatch path normally invokes `claude` (or codex/agy/gemini) via their
   respective CLIs. CLI processes have no mechanism to pause mid-run, receive
   an answer over HTTP, and resume; they read stdin once at startup and are
   otherwise one-shot.

2. **The Anthropic Agent SDK (`@anthropic-ai/sdk`) can.** The SDK's
   `canUseTool` callback provides a hook that fires before each tool call.
   By intercepting `AskUserQuestion` tool calls there, the sidecar can park
   the callback on a promise, wait for the operator's HTTP answer, then
   resolve the promise and let the agent continue. This is the only supported
   hook point for mid-run answer injection.

The consequence: answerable structured questions require a Node.js sidecar
process (the SDK engine), which the Go daemon spawns on demand. The Go daemon
is the authority for all HTTP routing, security enforcement, and transcript
persistence; the Node sidecar is responsible only for the SDK conversation
loop and the `canUseTool` intercept.

---

## Decisions

### Node sidecar rather than extending the CLI engine

The CLI path cannot be extended to support mid-run question answering without
restructuring it as a long-lived process with an answer channel — effectively
reimplementing what the SDK already provides. The SDK sidecar is the narrower
change.

The Go daemon remains the HTTP authority. The sidecar is an implementation
detail, not a new interface surface.

### Opt-in flag: `--console-structured-questions`

The feature is gated behind `yakos serve --console-structured-questions` and
is off by default. Rationale:

- It adds a Node.js runtime dependency. Operators without Node ≥18 on `PATH`
  should not see a broken daemon.
- The sidecar model introduces a new process to the daemon's supervision
  scope. Operators can audit and opt in explicitly.

When the flag is set and Node/the sidecar bundle is available, the daemon
builds an `SDKEngineFactory` at startup. When the flag is set but Node or the
bundle is missing, the daemon logs a WARNING and leaves the factory nil —
structured-question dispatch requests return 503, but the daemon starts
normally. The daemon does NOT fail startup on a missing Node dependency.

### `SDKEngineFactory` wired at startup, engines per-session

The factory is constructed once at daemon startup (resolving Node binary and
bundle path eagerly). Per-dispatch, `Manager.EnsureSDK` consumes the factory
to obtain an `SDKEngine` instance scoped to the conversation's session. This
avoids re-resolving Node on every dispatch while keeping engine lifetimes
session-scoped.

### Security model

**Owner-private questions.** The `ask_user_question` SSE event is routed
only to the session owner. `ChatHub.Route` enforces this via an explicit
carve-out for `ask_user_question` event types: even on shared conversations,
these frames are never forwarded to watchers.

**Server-recorded question shape.** The `pendingQuestionStore` records the
options and labels from the `ask_user_question` SSE frame at emission time.
`POST /api/chat/answer` validates incoming `answers` keys against this
server-side record. The client cannot supply or override the question shape
(forged-answer prevention).

**`toolUseId` binding.** Each pending question is keyed by `toolUseId`.
Answers with a mismatched `toolUseId` return 404 (not 400) so that pending
state is not leaked. A second answer to an already-consumed question returns
409 (single-use enforcement).

**Size caps.** `answers`, `response`, and `annotations` are all bounded to
`dispatch.MaxTaskBytes` before any processing.

**Owner-scope.** `POST /api/chat/answer` requires the caller to be the
conversation owner (403 for non-owners), using the same C1 dual-regime
identity resolution as `/api/chat/send`: cert CN wins in mTLS networked mode;
`operatorId` from the body is used on the loopback bearer path.

**RoleDispatch gate.** `/api/chat/answer` requires `RoleDispatch`, consistent
with all other chat mutation endpoints.

### AskUserQuestion is excluded from shared-session forwarding

`--console-structured-questions` composes safely with the share-pane feature:
even when a conversation is shared, `ask_user_question` frames are never
forwarded to watchers. This is enforced at the hub routing layer, not at the
question-store layer, so it holds regardless of whether the pending store is
populated.

## Consequences

**Positive:**

- Operators can answer `AskUserQuestion` inline in the Chat and IDE panes
  without switching to a terminal.
- The feature is strictly additive and opt-in: existing CLI-engine sessions
  and sessions without `--console-structured-questions` are unaffected.
- The daemon does not hard-fail on a missing Node dependency, preserving the
  zero-downtime degradation posture.
- The Go daemon remains the HTTP and security authority. The Node sidecar is
  scoped to the SDK conversation loop only.

**New risks and known limits:**

- **C1 — Node runtime dependency.** `--console-structured-questions` adds
  Node.js ≥18 as a runtime dependency for the structured-questions path.
  Operators using the binary-only install path must ensure Node is on `PATH`
  separately; `yakos doctor` should surface this check (follow-on).

- **C2 — Sidecar process supervision.** The daemon spawns the Node sidecar
  as a child process. Sidecar crashes return 503 for the affected session
  but do not crash the daemon. Sidecar lifecycle monitoring (restart-on-crash
  for long-lived engines) is a follow-on.

- **C3 — Single-use answer enforcement is non-idempotent.** A client that
  retries a POST to `/api/chat/answer` after a timeout (not knowing if the
  first request succeeded) will receive 409 on the retry. Callers should
  treat 202 and 409 as equivalent success for retry purposes.

- **C4 — `pendingQuestionStore` is in-memory.** Pending questions are not
  persisted across daemon restarts. A daemon restart while an
  `AskUserQuestion` is outstanding will lose the pending entry; the sidecar
  will time out or return an error to the agent.

---

## Alternatives considered

**Extend the CLI engine with a stdin-based answer protocol.**
The CLI engine (`claude --output-format stream-json`) has no stable hook for
mid-run answer injection. Any extension would require yakOS to own the
protocol, maintain it across `claude` CLI versions, and handle the case where
the CLI changes its streaming format. Rejected in favor of the SDK hook.

**Implement the SDK engine in Go using a third-party SDK port.**
No mature Go port of the Anthropic Agent SDK existed at decision time. The
`canUseTool` hook semantics are tightly coupled to the JS SDK's async model.
A Go reimplementation would be high-risk and high-maintenance. Rejected.

**Keep answering terminal-only; improve the UX with a console prompt.**
This keeps the architecture simple but breaks the in-browser workflow for
operators using the console as their primary interface. Rejected for UX
reasons, given the SDK hook already provides the integration point.

**Make structured questions always-on rather than opt-in.**
Rejected because the Node dependency is not universally available and the
daemon's zero-downtime degradation posture requires that missing optional
dependencies not prevent startup.
