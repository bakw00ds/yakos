# ADR-0007: Terminal REPL as a thin client of the console interactive engine (shared bidirectional session)

**Status:** Superseded by ADR-0008
**Date:** 2026-06-18
**Deciders:** operator — pending approval
**Refs:** `internal/start/start.go`, `internal/start/exec_unix.go`,
`internal/interactive/manager.go`, `internal/interactive/session.go`,
`internal/runtime/claude_interactive.go`, `internal/runtime/claude.go`,
ADR-0006 (Node Agent-SDK sidecar), `rule:cache-stability`

---

## Context

### Two independent Claude sessions today

`yakos start` resolves a project, prints a preflight banner, and then
`syscall.Exec`s the runtime CLI directly (`exec_unix.go:10`; the
`defaultExec` wrapper in `start.go:1111`). The Go process is replaced
entirely by the `claude` binary. yakOS retains no handle on the
resulting process: no conversationID reference, no session-ID binding,
no transcript ownership. The native `claude` TUI writes its own
transcript to `~/.claude/projects/…/*.jsonl`; yakOS does not read that
file.

The console web UI's Chat pane is driven by a completely separate
interactive engine. `interactive.Manager` (`manager.go`) maintains a
`map[conversationID]*managerEntry` of long-lived engine instances —
either a persistent `claude --print --input-format stream-json` CLI
process (`InteractiveExecCmd` in `claude_interactive.go`) or a Node
Agent-SDK sidecar (`sdk_engine.go`, introduced in ADR-0006). The daemon
owns the NDJSON transcript for these sessions (persisted under the
daemon's work directory; referenced in `chat_handler.go`).

These are two independent OS processes driving two independent Claude
sessions. PR #232 ("share by conversationId") is a browser-to-browser
watcher feature — it routes SSE events from one browser pane to another
for the same `conversationID` already managed by the daemon. It does not
connect the terminal REPL session to the daemon's interactive engine in
any way.

### Consequences of the current split

- A session started at the terminal (`yakos start`) cannot be shared
  into the web UI: the daemon has no knowledge of it.
- A session started from the browser Chat pane cannot be resumed at the
  terminal: there is no handoff protocol.
- Terminal and browser clients cannot co-drive one conversation.
  `Manager` enforces single-owner-per-conversationID semantics
  (`ErrOwnerConflict`, `manager.go:57-59`). Even if two callers
  attempted to `Ensure` the same conversation under different operators,
  the second would receive a 403. A shared-turn lock (`ErrTurnInFlight`,
  `session.go:327`) ensures that only one turn is in flight at a time;
  this is serialization per engine, not per protocol, so it applies
  regardless of which surface submitted the turn.

---

## Decisions

### Tier C: daemon owns the single interactive engine; terminal becomes a thin client

The daemon's `interactive.Manager` becomes the sole owner of Claude
interactive sessions. `yakos start` no longer `syscall.Exec`s the
`claude` TUI directly. Instead, the REPL path:

1. Starts (or verifies) the daemon.
2. Opens (or resumes) a daemon-owned `conversationID`.
3. Enters a terminal read-loop that:
   - Reads user input from stdin.
   - Submits it to the daemon via a local endpoint (e.g.
     `POST /api/chat/send`, the same endpoint the browser Chat pane
     uses, or a Unix-domain socket for the local case).
   - Streams the response back to the terminal for display.

The browser Chat pane is then naturally the same session. Sharing
between terminal and browser is structural, not a feature: both clients
talk to the same daemon-owned engine under the same `conversationID`.

The turn-serialization discipline (`ErrTurnInFlight`, `ErrOwnerConflict`)
remains the arbitration layer. When terminal and browser submit
concurrently, the second caller receives a 409; the terminal client
surfaces this as "a turn is already in progress; please wait."

---

## Consequences

### Positive

- Terminal and browser are naturally the same session. No
  synchronization protocol required beyond what the Manager already
  enforces.
- Transcript ownership is unified: the daemon's NDJSON record covers
  all turns regardless of which surface submitted them.
- The existing share-pane feature (PR #232) composes cleanly: a shared
  conversation is already shared to any SSE subscriber, terminal
  included, without further work.
- Turn arbitration is already implemented (`ErrTurnInFlight`,
  `ErrOwnerConflict`). The terminal client surfaces these as human-
  readable wait or conflict messages rather than HTTP status codes.

### New risks and costs

**C1 — Daemon is now a hard dependency of `yakos start`.**
Today `yakos start` works without a running daemon. Under Tier C, a
non-running daemon prevents the REPL from starting. This pairs with the
Phase-1 auto-spawn-daemon work: `yakos start` must detect a missing
daemon and either start it automatically or fail with a clear error.
Until auto-spawn lands, the operational contract changes.

**C2 — Loss of native TUI affordances.**
The bare `claude` TUI provides slash commands (`/clear`, `/compact`,
etc.), IDE attachment (`--ide`), and other CLI-native interactions. A
thin terminal client implementing only a text read-loop loses these
unless they are re-implemented or proxied. This is a new front-end
engineering surface for the project. Operators who rely on these
affordances will notice the regression unless a compatibility path is
provided (see "Legacy mode" below).

**C3 — Cache-stability constraint on shared sessions.**
`rule:cache-stability` requires that the shared conversation's cached
prefix — system prompt, agent body, tool definitions, roster — is
byte-identical regardless of which client (terminal or browser) submits
a turn. The terminal client and the browser Chat pane must resolve to
the same composed agent body for the shared `conversationID`. The
mechanism: the daemon composes the agent body once at session creation
(as `--append-system-prompt` in `InteractiveExecCmd`; see
`claude_interactive.go:63` and the `AgentSystemPrompt` field on
`ChatDispatchRequest` in `claude.go:742`). The terminal client must not
independently recompose or substitute a different agent body when
joining an existing conversation; it must use the daemon-owned session
rather than start a new one. Any deviation breaks the Anthropic prompt
cache for every turn after the first mismatch.

**C4 — Turn arbitration UX.**
When terminal and browser submit turns concurrently, exactly one
proceeds; the other receives `ErrTurnInFlight` (409). The terminal
client must surface this as a clear human-readable message ("a turn is
already in progress from another client; please wait") rather than
crashing or hanging. Polling or a WebSocket upgrade are implementation
choices; the policy is already defined by the Manager's existing
serialization.

**C5 — Migration and coexistence.**
The existing direct-exec REPL path (`NoREPL == false` in `start.go`)
must be preserved as a legacy fallback behind a flag (e.g.
`yakos start --direct` or `--no-daemon`) for the transition period.
Operators on environments without a running daemon, or who rely on
native TUI features (C2), must not be stranded. The legacy path can be
deprecated and removed once the thin-client path achieves feature parity
and auto-spawn is stable.

## Alternatives considered

### Tier A: read-only mirror (browser tails terminal transcript)

The browser chat pane would tail the native `claude` TUI's transcript
file (`~/.claude/projects/…/*.jsonl`) and display it. Input remains
terminal-only.

Feasible: the file is written continuously and could be polled or
watched. Does not require protocol changes.

Rejected: input is permanently one-way. The browser pane becomes a
passive observer only. Operators cannot submit turns from the browser,
which is the primary goal of shared sessions. Transcript format
differences between the CLI's native JSONL and the daemon's NDJSON
schema would require ongoing translation work.

### Tier B: two independent drivers co-driving one conversation

Both the terminal REPL (via native `claude` TUI) and the browser pane
(via the daemon's `interactive.Manager`) send turns to the same Claude
`conversationID` simultaneously.

Infeasible. Claude's conversation model is not designed for concurrent
writers. More concretely:

- `interactive.Manager` enforces single-owner-per-conversationID:
  `ErrOwnerConflict` (`manager.go:57-59`) prevents a second `Ensure`
  call for the same `conversationID` from a different operator.
- The CLI-native TUI and the daemon's interactive engine are separate
  OS processes with no shared turn-ordering mechanism. Concurrent
  writes to the same conversation produce undefined model behavior.
- The cached prefix constraint (`rule:cache-stability`, C3 above)
  cannot be satisfied if two independent processes each independently
  construct and submit the system prompt — they would produce the same
  bytes only by accident.

Rejected: fundamentally incompatible with the Manager's single-owner
model and the cache-stability requirement.

---

## Required gates before implementation

1. Operator (human) approval of this ADR.
2. Phase-1 auto-spawn-daemon work lands or a clear plan for daemon
   startup dependency is agreed (C1).
3. Terminal client API contract agreed (HTTP endpoint vs. Unix socket;
   streaming protocol; auth regime for loopback).
4. Legacy direct-exec fallback path (`--direct` flag or equivalent)
   implemented and documented before the new path is the default (C5).
5. Cache-stability audit: confirm that `conversationID`-keyed session
   reuse in `Manager.Ensure` never re-submits the `agentSystemPrompt`
   after session creation (C3). The Manager's `Ensure` returns the
   existing engine on subsequent calls; `InteractiveExecCmd` is only
   called at engine creation. This must remain true after any
   thin-client wiring is added.
