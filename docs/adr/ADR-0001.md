# ADR-0001: In-project commit-keyed metrics history store

**Status:** Accepted
**Date:** 2026-06-11
**Deciders:** yakOS backend specialist (Phase-1 metrics MVP)

---

## Context

The `yakos metrics` subsystem needs to persist a time series of code-quality,
effectiveness, and security snapshots. Each snapshot is keyed to a git commit
SHA so snapshots can be correlated with source history, compared across
commits (`yakos metrics compare`), and trended over time.

Two storage models were considered:

1. **Centralized in `~/.yakos-state/`** — alongside the dispatch log and other
   operator-scoped state files.
2. **In-project at `<project>/.yakos/metrics/history.ndjson`** — committed to
   the project's own git history.

The data has two distinct origin layers:

- **Inputs are host-local.** The dispatch log (`~/.yakos-state/dispatch-log*.ndjson`),
  model-routing candidates, and retro artifacts live in `~/.yakos-state`. They
  reflect the operator's local session history and do not move with the project.
- **Derived, commit-keyed history is project-specific.** Coverage percentages,
  lint finding counts, dead-code symbols — these are properties of a specific
  commit in a specific project. They have the same lifecycle as the source code
  they describe.

Existing yakOS precedent: `plan-quality-log.ndjson` is stored in-project
(committed), while `dispatch-log.ndjson` is operator-local. This ADR follows
that split.

A new on-disk pattern requires an ADR per `rule:no-new-patterns-without-ADR`.

---

## Decision

Store metrics history as an **append-only NDJSON file** at
`<project>/.yakos/metrics/history.ndjson`, committed to the project repo.

One JSON line per snapshot. Each line encodes a `Snapshot` struct with:
- `schema: "yakos.metrics/v1"` (version tag for future migration)
- `commit` (full SHA), `branch`, `ts` (RFC3339 UTC), `trigger`
- `profiles[]` — detected stack profiles
- `metrics` — all metric categories (pointer fields: null = not measured, 0 = measured zero)
- `tool_status` — map of tool name → "ok" | "tool-missing" | "error"

Write is `O_APPEND|O_CREATE` — a single JSON line is under PIPE_BUF (4 KiB on
Linux, 512 bytes on POSIX minimum) so concurrent appends from parallel collect
runs are atomic on POSIX. This matches the `plan-quality-log.ndjson` pattern.

**Key invariant:** `null` (metric pointer is nil) means "not measured". `0`
(metric pointer points to zero) means "measured, result is zero". This
distinction is load-bearing — it's how `yakos metrics report` distinguishes a
missing tool (`coverage_pct: null`) from a project with no test coverage
(`coverage_pct: 0`). Never coerce nil→0.

---

## Consequences

**Positive:**

- History travels with the project. A clone of the repo includes its metrics
  history, enabling CI systems, new team members, and the `compare` verb to
  work on the full dataset without operator-local state.
- Commit correlation is first-class. The `commit` field makes `git log`-style
  navigation natural.
- `yakos metrics compare <shaA> <shaB>` works correctly even on machines that
  have never run `yakos metrics collect` — the history is already in the repo.
- Simple implementation: no database, no network, grep-friendly.

**Negative / tradeoffs:**

- Metrics files accumulate in the repo over time. Operators who snapshot on
  every commit will see `history.ndjson` grow. Phase-2 should add a rotation
  or pruning strategy.
- Host-local signals (dispatch cost, first-try success rate) are mixed with
  in-project signals (coverage, lint). Lines collected on a different machine
  will have null efficiency fields. This is expected and documented in the
  schema.
- The `~/.yakos-state/dispatch-log` boundary means efficiency metrics are
  always null in CI environments (no local dispatch log). Phase-2 can add a
  CI-specific signal source.

**Deferred:**

- History pruning / rotation (Phase-2).
- Cross-machine efficiency signal aggregation (Phase-2).
- `yakos metrics gate` CI integration (Phase-2 stub implemented, not functional).
