# ADR-0002: Embedded-lib materialization and root-resolution pattern

**Status:** Accepted
**Date:** 2026-06-11
**Deciders:** yakOS Go-port specialist (v0.39.0.0 binary-install milestone)
**Refs:** #135 (`feat(install): embed lib/ so binary-only installs are self-sufficient`)

---

## Context

yakOS ships a framework library (`lib/agents/`, `lib/skills/`,
`lib/rules/`, `lib/hooks/`) that must be present on disk for the CLI
to work: agent composition, hook installation, symlink wiring, and
`yakos validate` all traverse the lib tree at runtime.

Up to v0.38, the framework assumed a cloned repo at a path pointed to
by `YAKOS_ROOT`. This broke `curl|sh` binary-only installs, where no
repo clone exists. Operators hit "YAKOS_ROOT is not set" errors and had
to clone the repo separately just to use a pre-built binary.

Three approaches were considered:

1. **Require a repo clone for all installs.** Simple but defeats the
   purpose of shipping a compiled binary. Operators would still need Git
   and network access to the repo on every machine.

2. **Embed lib in the binary and serve from the embedded FS directly.**
   The `//go:embed` FS is read-only at the Go level. Many CLI commands
   write back into lib (e.g. `yakos teach`, hook-install into
   `lib/hooks-user/`, project-level agent overrides). Serving entirely
   from an embedded FS would require adding a virtual layer for writes,
   adding complexity with no benefit over option 3.

3. **Embed lib in the binary; materialize to disk on first `yakos install`.**
   The binary carries a full snapshot of `lib/` via `//go:embed`. On
   install, the lib tree is extracted to a stable user-owned directory.
   Subsequent commands use the on-disk copy normally. Live repo clones
   still take precedence when present.

Option 3 was chosen.

---

## Decision

**Embed** the full `lib/` tree into the Go binary at build time via
`//go:embed lib/` (staged by `make embed-lib`, which copies from the
repo root into `cli-go/internal/framework/embed/lib/`).

**Materialize** the embedded lib to disk at `~/.local/share/yakos/<version>/`
when `yakos install` runs and no on-disk repo is available. A version-stamp
file (`.yakos-embedded-version`) is written inside the directory; subsequent
installs skip extraction if the stamp matches the running binary's version.

**Resolve** the framework root via `install.ResolveRoot()` with the
following precedence cascade:

1. `YAKOS_ROOT` env var — if set and `$YAKOS_ROOT/lib/` exists, use it.
   This is the developer / live-edit path. Edits to agents, hooks, and
   rules take effect immediately without rebuilding.
2. Exe-adjacent repo clone — if the binary lives inside a directory
   containing `lib/`, use that directory. This covers the "binary
   installed inside a repo clone" case automatically.
3. Embedded lib (materialized) — if neither of the above applies and
   the binary carries the embedded lib (`framework.HasEmbeddedLib()`),
   materialize to `~/.local/share/yakos/<version>/` and return that
   path. This is the `curl|sh` binary-only path.
4. Error — no lib found anywhere; emit an actionable message telling
   the operator to set `YAKOS_ROOT` or use a release binary.

The version-directory layout (`~/.local/share/yakos/0.39.0.0/`,
`~/.local/share/yakos/0.40.0.0/`, ...) means multiple binary versions
can coexist without conflict. Old version directories are not deleted
automatically; operators clean them if disk space is a concern.

`scripts/install.sh` runs `yakos install` after placing the binary, so
the lib is materialized as part of the install flow. The installer also
persists `export YAKOS_IMPL=go` to the user's shell profile so the Go
binary is activated for all future shells.

---

## Consequences

**Positive:**

- Binary-only installs are fully self-contained. A `curl|sh` install on
  a machine without Git or network access to the yakOS repo works end-to-end.
- The developer workflow (live `lib/` via `YAKOS_ROOT` or exe-adjacent
  repo) is unchanged. Agents and hooks edited in the repo take effect
  immediately — no rebuild needed.
- The version-directory layout makes rollback straightforward: install
  the previous binary; `yakos install` materializes its embedded lib into
  its own slot.
- Idempotent: re-running `yakos install` at the same version is a no-op
  (version stamp matches). The `--force` flag bypasses this for recovery.

**Negative / tradeoffs:**

- For binary installs, updating the lib requires updating the binary.
  There is no way to hot-patch a lib file without either setting
  `YAKOS_ROOT` to a live repo or rebuilding the binary. This is an
  explicit tradeoff: binary installs trade flexibility for simplicity.
- The embedded lib snapshot is baked at build time by `make embed-lib`.
  If `lib/` changes after a release binary is cut, those changes are not
  visible to binary-install operators until the next release.
- Old version directories at `~/.local/share/yakos/<old-version>/`
  accumulate silently. Operators who upgrade frequently should periodically
  clean them. A future `yakos install --prune-old` flag is tracked but
  not yet shipped.
- On Windows without symlink privileges, `yakos install` falls back to
  junctions (directories) or file copies rather than real symlinks. The
  materialization step itself is symlink-free and works on all platforms.
