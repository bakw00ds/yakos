# ADR-0004: Networked multi-operator identity layer

**Status:** Proposed
**Date:** 2026-06-13
**Deciders:** operator review required before implementation begins
**Refs:** `docs/unified-console-plan.md`, `internal/mtls/`, ADR-0003 (flows identity model)

---

## Context

yakOS's console and dispatch stack today binds exclusively to loopback.
Access control is a single self-asserted bearer token; `operator_id` is
whatever the caller claims, which is cooperative labeling among
uid-equivalent teammates on the same host. This is acceptable under the
loopback-only threat model: all callers share the same UID and the OS
enforces the network boundary.

The operator now wants to bind the console and dispatch daemon to
non-loopback addresses so it is reachable from other hosts. This changes
the threat model in one critical way: **chat-pane / dispatch access from
the network is functionally RCE-equivalent** because the dispatch path
can invoke agents with `bypassPermissions`-equivalent authority. The
existing single self-asserted bearer token is not an acceptable gate for
a networked daemon.

Two deployment models must be simultaneously supported:

1. **Multi-instance (existing, unchanged):** independent daemons
   coordinating via git and `work/` artifacts. Each daemon is loopback-
   only; the current auth model is untouched.

2. **Multi-operator on one networked daemon (new):** a single daemon
   bound to a non-loopback address, with real per-user identity and
   per-route authorization.

The `internal/mtls/` package is already present in the tree. It
generates a persisted self-signed CA at `~/.yakos-state/mtls/`, issues
a server cert and per-client certs, and its package doc already states
the target invariant: "loopback uses bearer token; non-loopback REQUIRES
mutual TLS; daemon refuses to bind non-loopback without CA+cert." This
ADR formalizes the full decision around that existing foundation.

This change is security-sensitive per `rule:pr-conventions`. It requires
a security-reviewer pass and operator (human) approval of this ADR
before any networked code is written.

## Decisions

### Authentication: mTLS client certificates via `internal/mtls/`

Off-loopback, authentication is **mutual TLS**. The in-tree `internal/mtls/`
package is the implementation — no new auth library is introduced.

- The client certificate's Common Name becomes the authenticated
  `operator_id`.
- The mTLS CA is the same self-signed CA already generated at
  `~/.yakos-state/mtls/` on first non-loopback start.
- Per-user bearer tokens are kept as a documented fallback
  (`--auth=token`) for headless/CI consumers sitting behind a
  trusted reverse proxy. They are not a standalone option for
  networked operator sessions.
- OIDC/SSO is explicitly rejected: it imports an external IdP
  dependency that is disproportionate for an operator tool (see
  Alternatives considered).

### Transport: in-process TLS; reverse proxy as a documented alternative

The daemon serves TLS directly via the mtls package's CA-issued server
cert. A reverse proxy (nginx, Caddy, Tailscale) in front is a documented
alternative but is not assumed by the daemon.

Plain HTTP off-loopback is forbidden and cannot be enabled by any flag.
The console's derived WebSocket origin must switch from `ws://` to
`wss://` when the daemon is bound off-loopback.

### Authorization: four-role RBAC enforced at two points

Four roles, ordered by privilege:

| Role | Permitted actions |
|---|---|
| `read` | View Overview, Cost, Perf, Kanban; read own and shared transcripts |
| `dispatch` | Open chat panes; run agent dispatches |
| `flows-run` | Trigger and resume workflows (higher stakes: fan-out cost) |
| `admin` | Cert/token rotation, bind config, future client enrollment |

Authorization is enforced at **two points** (defence-in-depth):

1. **Console edge middleware** — for read-only routes that never
   reach the dispatch facade.
2. **`dispatch.Service` facade** — for `dispatch` and `flows-run`
   routes. This is the existing single chokepoint; the RBAC check
   is added here, not in a parallel path.

The generalized read/write scheme the REST API already models is
extended; no parallel authorization mechanism is introduced.

### The loopback / non-loopback invariant

| Bind address | Auth model |
|---|---|
| Loopback (`127.0.0.1`, `::1`) | Existing bearer-token cooperative labeling — unchanged |
| Non-loopback | mTLS REQUIRED; RBAC REQUIRED; daemon refuses to bind without both |

Fail-closed: the daemon refuses to start a non-loopback listener unless
mTLS material is present and an authz mode is configured.

### Authenticated audit: `operator_id` override off-loopback

Off-loopback, the edge derives `operator_id` from the verified client-
cert CN and **overrides** any caller-supplied value before it reaches
`dispatch.Service`. This extends the existing reserved-prefix pattern
("server overrides caller-claimed identity") so that an authenticated
identity is non-overridable.

**Dual-regime documented explicitly:** On loopback, `operator_id` remains
cooperative labeling (caller-supplied). Off-loopback, it is
cryptographically bound to the client cert. The NDJSON dispatch log
therefore has two audit regimes depending on bind address. Tests must
cover both regimes; conflating them is an audit-trail correctness trap
(see Consequences C3).

### Bind UX: loud, fail-closed `--console-bind`

The flag is `--console-bind <addr>`, consistent with kanban's
`--allow-all-interfaces` precedent.

On a non-loopback address the daemon must, in order:

1. Refuse without mTLS material configured.
2. Refuse without an authz mode configured.
3. Print a startup banner that states: networked mode is active, the
   server cert fingerprint, and the active authz model.

There is no `--insecure-no-tls` escape hatch for non-loopback binds.

## Consequences

**Positive:**

- Real per-user identity and an auditable `operator_id` field in the
  dispatch log for networked sessions.
- Reuses the in-tree `internal/mtls/` package — no new auth library;
  the CA generation and cert issuance path already exists.
- The loopback path is entirely unchanged. Existing single-operator and
  multi-instance deployments require no migration.
- Defence-in-depth RBAC (edge + facade) means a middleware bypass does
  not automatically grant dispatch access.
- Fail-closed startup prevents an accidental non-loopback bind without
  auth material.

**Negative / risks:**

- **C1 — Share-pane confidentiality is a live hole the moment the bind
  is networked.** Chat-pane ownership currently trusts caller-supplied
  `operatorId`. Authenticated identity (this ADR) is a hard precondition
  for fixing that hole, not a follow-up. The share-pane ownership model
  must be updated alongside or before the networked bind ships — it
  cannot be deferred.

- **C2 — Client cert distribution/enrollment is an unsolved human-
  factors problem.** There is no enrollment endpoint today; adding one
  is new attack surface. Until a safe enrollment flow is designed, the
  operator must distribute client certs out of band. The administrative
  burden is real and must be documented prominently in the UX.

- **C3 — The dual `operator_id` regime is an audit-trail correctness
  trap.** Code that reads the dispatch log must not assume
  cryptographically-verified identity on loopback entries. This requires
  explicit tests covering both regimes and clear documentation in the
  NDJSON schema. Conflating the two is a silent correctness failure, not
  a loud error.

- **C4 — `bypassPermissions`-equivalent RCE reachable from the
  network.** Fail-closed startup and the two-point RBAC are the only
  technical guards. There is no sandboxing boundary added by this ADR.
  The security-reviewer pass required below exists precisely because the
  consequence of a gap here is full remote code execution.

**Deferred / follow-on:**

- Client cert enrollment endpoint (design separately; treat as new
  attack surface requiring its own security review).
- Per-role audit log (currently the dispatch log records what ran, not
  which role authorized it; adding a `role` field to NDJSON entries is
  a future extension).
- Share-pane ownership model update (C1 above; must ship with or before
  the networked bind, not after).

**Required gates before any networked code ships:**

1. Operator (human) approval of this ADR.
2. Security-reviewer pass on the implementation PR (per
   `rule:pr-conventions`).
3. Red-team / security pass covering the non-loopback bind, mTLS
   handshake, RBAC enforcement, and the `operator_id` override path.
4. Explicit tests for the dual `operator_id` regime (C3).

## Alternatives considered

**Per-user bearer tokens as the primary auth mechanism.**
Replayable; no cryptographic binding to the transport; requires an
issuance and revocation store the project does not have. Kept only as a
CI/headless fallback (`--auth=token`) behind a trusted proxy, not as a
standalone option for networked operator sessions.

**OIDC/SSO.**
Imports an external IdP dependency. Configuration surface, operational
complexity, and failure modes are disproportionate for an operator tool
used by a small team. Explicitly rejected; revisit if the operator count
grows to the point where a centralized directory is warranted.

**Reverse-proxy-only (no in-process TLS).**
Supported as a documented alternative but not assumed. Relying solely on
a reverse proxy leaves a second moving part outside the daemon's control.
If the proxy is misconfigured or bypassed, the daemon has no TLS layer
of its own. In-process TLS via the existing mtls package is the default.
