# ADR-0008: Native `claude` TUI shared between terminal and web via daemon-owned PTY

**Status:** Accepted — supersedes ADR-0007
**Date:** 2026-06-18
**Deciders:** operator (approved)
**Refs:** `internal/start/start.go`, `internal/start/exec_unix.go`,
`internal/jsonrpc/socketpath.go`, `internal/serve/serve.go`,
`internal/consoleui/ws_handler.go`, `internal/netid/netid.go`,
ADR-0007 (context and Tier A/B rejection rationale), ADR-0005 (hybrid auth)

---

## Context

See ADR-0007 §Context for the full current-state description. The
operative facts are:

- `yakos start` replaces the Go process with the native `claude` TUI via
  `syscall.Exec` (`exec_unix.go:10`; `defaultExec` wrapper in
  `start.go:1111`). yakOS retains no handle on the resulting process.
- The console web UI Chat pane is driven by a separate daemon-owned
  interactive engine (`interactive.Manager`, `manager.go`). The daemon
  process runs the console HTTP/WS server internally
  (`serve.go:780` — `consoleui.New` call). Default bind:
  `127.0.0.1:7890`.
- The daemon also listens on a per-workspace JSON-RPC Unix socket
  (`jsonrpc/socketpath.go:26` — `SocketPath(workspaceRoot)`) used for
  local IPC between yakOS subcommands and the daemon.
- Terminal and browser are two independent OS processes driving two
  independent Claude sessions today, with no handoff protocol.

The operator's goal — established after reviewing the Tier C approach
recorded in ADR-0007 — is to share the **native** `claude` TUI between
terminal and browser, not to replace it with a structured re-
implementation. ADR-0007's Tier C (thin terminal client) is discarded
precisely because it loses native TUI affordances (ADR-0007 C2): slash
commands, IDE attachment, and other CLI-native interactions that
operators rely on.

---

## Decision

### PTY topology: T1 — daemon owns the PTY master

The daemon spawns `claude` under a pseudo-terminal (PTY) that it owns.
`yakos start` becomes a thin local PTY client: instead of `syscall.Exec`
replacing the Go process with `claude`, it dials the daemon's Unix
socket (`jsonrpc/socketpath.go:26`), requests a new (or resumed) PTY
session, and enters a local pump loop that:

- Forwards keystrokes from the local terminal's stdin to the daemon over
  the socket.
- Forwards PTY output from the daemon back to the local terminal's
  stdout/tty.
- Forwards `SIGWINCH` (terminal resize) as resize frames to the daemon.

The daemon relays PTY output to any connected WebSocket viewers (see
`/v1/term/<sessionId>` below) in addition to the local pump.

**Why T1 beats T2 ("start.go owns the PTY master").**

T2 would have `start.go` own the PTY master (as today's syscall.Exec
path owns the terminal), with the daemon reaching into the `start.go`
process's PTY fd to serve browser viewers. This inverts the supervision
hierarchy in three ways that make it unworkable:

1. **FD reach-back.** Passing an open PTY fd from a transient `yakos
   start` process to a long-lived daemon requires either
   `SCM_RIGHTS`-passing over a Unix socket or a `/proc/PID/fd/N` path.
   Both add fragile OS-specific coupling.
2. **Two hops for every byte.** Browser output would travel: PTY master
   (start.go) → socket → daemon → WebSocket → browser. Compared to T1
   (PTY master is in the daemon, one hop to WebSocket), T2 doubles the
   relay path for every byte.
3. **Lifecycle inversion.** The daemon is the long-lived supervisor. If
   `yakos start` (the transient process) owns the PTY master, the daemon
   cannot outlive the terminal session, nor cleanly restart without
   destroying all active PTY sessions. T1 preserves the correct
   hierarchy: daemon outlives any single terminal client.

### New WebSocket endpoint: `/v1/term/<sessionId>`

A dedicated binary-framed WebSocket endpoint serves PTY I/O to
browser viewers. It is separate from `/v1/events`
(`ws_handler.go:93` — the existing JSON text-event bus), which is left
entirely untouched.

**Frame format (binary WebSocket frames, `x/net/websocket`):**

Outbound (daemon → client):

| Byte 0 | Payload |
|--------|---------|
| `0x00` | Raw PTY bytes |
| `0x01` | Close: 4-byte big-endian exit code |

Inbound (client → daemon):

| Byte 0 | Payload |
|--------|---------|
| `0x10` | Keystrokes (raw bytes) |
| `0x11` | Resize: 2-byte cols (big-endian) + 2-byte rows (big-endian) |

`x/net/websocket` is already in `go.mod` (line 10: `golang.org/x/net
v0.55.0`). Binary frames require no new WebSocket dependency.

### Auth chain: reuse verbatim

The `/v1/term/<sessionId>` handler reuses the existing WS middleware
stack without modification:

- **Loopback path:** `consoleLoopbackOnly` + `consoleOriginAllowList` +
  `consoleAuthSubprotocol` — identical to the loopback mount of
  `/v1/events` at `ws_handler.go:171-179`.
- **Networked path:** `consoleOriginAllowListNetworked` +
  `consoleAuthSubprotocolOrSession` (`ws_handler.go:465-515`).
- **Identity resolution:** `netid.Resolver` — loopback cooperative
  bearer → `RoleAdmin` (`netid.go:567-580`); certless/sessionless
  networked → `RoleNone` fail-closed (`netid.go:583-595`).

**Writer gating.** Inbound keystroke frames (`0x10`, `0x11`) are
accepted only from callers with `RoleAdmin`. This is the primary
mitigation for the raw-remote-drive threat (see Consequences C3 below).
Read-only output viewers (`0x00` frames outbound only) are permitted at
`RoleRead`.

**Opt-in flag.** The `/v1/term/<sessionId>` endpoint and PTY sharing
are behind `yakos serve --share-terminal`, which is **off by default**.
The networked-write path (browser keystrokes to a non-loopback daemon)
requires explicit opt-in AND an authenticated admin session (ADR-0005
hybrid auth).

**`--direct` legacy path.** The existing `syscall.Exec` path in
`start.go` is preserved behind `yakos start --direct` for the entire
transition period. Operators on environments without a running daemon,
or who prefer the zero-daemon terminal experience, are not stranded.

### Browser: additive "Terminal" pane (xterm.js)

A new "Terminal" pane is added to the console UI alongside the existing
Chat and IDE panes. It renders PTY output using
[xterm.js](https://xtermjs.org/), vendored into
`internal/consoleui/dist/vendor/` alongside Monaco. This pane is
strictly additive: the existing Chat pane, its engine, and its API
surface are untouched.

### Implementation phases

| Phase | Scope |
|-------|-------|
| P0 | Spike: daemon PTY ownership + local pump viability; `x/net/websocket` binary-frame throughput benchmarked before MVP commit |
| P1 | Read-only browser mirror: daemon spawns `claude` under PTY, `/v1/term/<sessionId>` streams `0x00` frames to browser viewers; `RoleAdmin` gate; `--share-terminal` flag; `--direct` preserved |
| P2 | Bidirectional: local pump (`yakos start` ↔ daemon Unix socket) + browser inbound keystrokes (`0x10`/`0x11`); writer-auth security review before any inbound path ships |
| P3 | Multi-viewer hardening, networked-write second security review, `--direct` deprecation notice |

## Consequences

### Positive

- **Native TUI fidelity preserved.** Slash commands, IDE attachment
  (`--ide`), and all other `claude`-native interactions work unchanged
  inside the daemon-owned PTY. This is the property ADR-0007's Tier C
  sacrificed (ADR-0007 C2), and the primary reason this ADR supersedes
  it.
- **Browser fan-out is in-process.** The daemon owns the PTY master and
  the WebSocket server in the same process — no inter-process
  coordination for viewer delivery.
- **Auth chain reused verbatim.** No new authentication logic;
  `/v1/term/<sessionId>` rides the same middleware stack as `/v1/events`.
- **Chat pane untouched.** The existing interactive engine
  (`interactive.Manager`), Chat pane, and all related APIs are
  unaffected.
- **Cache-stability is not a concern.** The daemon spawns `claude` once
  under the PTY and streams raw bytes to all viewers. There is no per-
  turn system-prompt recomposition and no shared-prefix cache issue.
  This is structurally simpler than ADR-0007 C3.

### New risks and known costs

**C1 — Daemon is a hard dependency of `yakos start`** (carried from
ADR-0007 C1). Under the PTY model the daemon must be running for `yakos
start` to use the PTY path. The `--direct` fallback mitigates the
operational impact during the transition. Auto-spawn-daemon work
(Phase-1 dependency) must land before `--direct` can be deprecated.

**C2 — PTY supervision fidelity work.** Replacing `syscall.Exec` with
daemon-supervised PTY spawning requires careful handling of:

- Signal forwarding: `SIGTERM`, `SIGINT`, `SIGQUIT` from the local
  terminal must reach the `claude` child in the daemon; they must not
  silently disappear at the pump boundary.
- `SIGWINCH` / resize: the local pump sends `0x11` resize frames; the
  daemon must call `pty.Setsize` on the PTY master; the `claude` process
  must receive `SIGWINCH`. Correct terminal dimensions are required for
  TUI rendering.
- Exit code propagation: the daemon must relay the `claude` exit code
  to the local pump so `yakos start` exits with the same code.
- TTY restore: on abnormal disconnection (daemon crash, network loss),
  the local terminal's tty state (`stty sane`) must be restored. The
  pump must install a cleanup handler.

**C3 — Primary security threat: raw remote drive of a
`bypassPermissions` process.** The native `claude` TUI is launched with
`--permission-mode bypassPermissions` (`start.go:1017`). A browser
operator with inbound-keystroke access can execute arbitrary filesystem
operations on the host. Mitigations, in order of strength:

1. **Writer gating to `RoleAdmin` only.** Only authenticated admins can
   send `0x10`/`0x11` frames. This applies on both loopback (cooperative
   bearer → `RoleAdmin`) and networked (authenticated session +
   `RoleAdmin` role check).
2. **Opt-in flag `--share-terminal`.** The endpoint is not mounted
   unless explicitly enabled.
3. **Startup banner warning.** When `--share-terminal` is active on a
   networked daemon, a prominent banner (modeled on the
   `--console-allow-bash` warning at `serve.go:770-778`) is printed to
   stderr.
4. **Networked write requires ADR-0005 hybrid auth.** A networked
   browser operator must present a valid authenticated identity
   (`RoleAdmin`) per the `netid.Resolver` precedence at
   `netid.go:421-595`. Certless/sessionless requests receive
   `RoleNone` (`netid.go:583-595`) and are rejected at the writer gate
   before any keystroke frame is processed.
5. **Security-reviewer pass before P2 ships** (see Required Gates).

Despite these mitigations, the residual risk is real: `--share-terminal`
on a networked daemon with a compromised admin credential gives the
attacker a full interactive shell inside a `bypassPermissions` process.
Operators must treat this flag with the same care as
`--console-allow-bash`.

**C4 — New third-party dependency: `creack/pty`.** PTY allocation and
`SIGWINCH`/resize handling require OS PTY APIs not covered by the
standard library. `go.mod` (lines 10, 12: `golang.org/x/net`,
`golang.org/x/sys`) contains no PTY library today. `github.com/creack/pty`
is the standard Go PTY library, but adding it requires an explicit
operator approval gate (see Required Gates item 1).

**C5 — Multi-viewer byte interleaving.** When multiple browser viewers
watch the same PTY session simultaneously, each receives the raw PTY
byte stream independently. This is accepted shared-terminal semantics
(same as `tmux` attach or `screen -x`). No additional coordination is
needed; the daemon broadcasts `0x00` frames to all connected `/v1/term`
viewers for the session.

## Alternatives considered

See ADR-0007 §Alternatives considered for the Tier A (read-only file
mirror) and Tier B (two independent drivers) rejection rationale. Both
remain rejected for the same reasons documented there.

**Tier C: daemon-owned interactive engine, thin terminal client
(ADR-0007 Decision).** Discarded. Loses native TUI affordances — the
rejection criterion that motivated this ADR. Recorded in ADR-0007 as a
first-class alternative for operators who do not require native TUI
fidelity.

**T2: start.go owns the PTY master.** `yakos start` keeps PTY
ownership; the daemon reaches in via `SCM_RIGHTS` fd-passing or
`/proc/PID/fd/N` to serve browser viewers. Rejected: fd reach-back is
OS-specific and fragile; every browser byte travels two hops (start.go
→ daemon → browser); lifecycle is inverted (daemon depends on the
transient start.go process). See the T1 vs T2 analysis in the Decision
section above.

**PTY frames over `/v1/events`.** Multiplexing PTY bytes onto the
existing JSON-text event bus (`ws_handler.go:93`) rather than a
dedicated `/v1/term` endpoint. Rejected for two reasons: (a) the
existing text-drain loop discards inbound frames after the hello message
(`ws_handler.go:200-230`) — adapting it for bidirectional binary PTY
frames would break the invariant that `/v1/events` connections are
read-only from the client's perspective; (b) base64-encoding PTY bytes
into JSON fields to fit the text-frame protocol would add ~33% wire
overhead and decoding latency on every keystroke.

## Required gates before implementation

1. **Operator approval of this ADR and of adding `creack/pty` to
   `go.mod`.** The PTY dependency is the minimum new third-party surface
   for the PTY ownership model. It must be explicitly approved before
   any implementation PR.

2. **Phase-0 spike resolves `x/net/websocket` binary-frame throughput
   before MVP commit.** The existing WS stack uses text frames for
   `/v1/events`; binary-frame throughput at PTY-output rates (up to
   ~1 MB/s for fast-scrolling output) must be confirmed adequate before
   the architecture is locked.

3. **Security-reviewer pass on writer-auth before any inbound keystroke
   path ships (P2).** The pass must cover: `RoleAdmin` gating on
   `0x10`/`0x11` frames, keystroke path from WebSocket frame to PTY
   master write, and the `--share-terminal` banner warning. A second
   security-reviewer pass is required before networked write is enabled
   in P3.

4. **`--direct` legacy exec path preserved and documented before the
   daemon-owned PTY path becomes the default.** Operators must have a
   working fallback throughout the transition. `yakos start --direct`
   must produce a visible deprecation notice (not a silent removal)
   when the PTY path is ready to become default.

## Amendment (2026-06-18): Phase 1 topology changed T1 → login-shell-owned PTY (T2-relay)

**Operator decision:** selected during an in-session prompt ("Re-architect
to login-shell-owns-PTY"). The ADR's overall Status remains **Accepted**;
the T1 topology chosen in the Decision section above is superseded for
Phase 1 by the T2-relay model described here.

### Root cause: daemon EPERM on hardened hosts

Production testing on a hardened GCP host revealed that the detached
daemon **cannot `fork/exec` `claude`** — it receives `EPERM` from the
host's seccomp/AppArmor policy inherited at daemonization time. The
same `claude` binary executes without error from the operator's **login
shell** (`yakos start --direct` confirmed this). The policy applied to
the detached daemon's syscall surface does not apply to processes
launched from an interactive login shell. T1 is therefore unworkable
on any host where daemons run under a restricted execution policy that
login shells are exempt from.

The three T2 rejection arguments in the Decision section above (FD
reach-back; two-hop relay; lifecycle inversion) were correct as
originally written but assumed the daemon retained exec permission.
That assumption does not hold on hardened hosts. See the original T2
"Alternatives considered" entry for the reasoning now partially
reversed.

### New Phase-1 model: T2-relay ("external session")

`yakos start --share-terminal` is the entry point. It runs in the
**operator's login shell** — which has exec permission — and owns the
PTY master and the `claude` child process directly. The daemon is
promoted to a **relay** rather than an owner.

**Phase-1 data flow:**

```
[login shell]
  yakos start --share-terminal
       │
       ├─ openpty()  ←── allocates PTY master/slave (login shell — exec permitted)
       ├─ forkexec(claude, slave)  ←── claude attached to PTY slave
       │
       ├─ local raw-mode passthrough
       │    stdin  ──→  PTY master write   (operator keystrokes → claude)
       │    PTY master read  ──→  stdout   (claude output → local terminal)
       │
       └─ PTY output mirror over owner-only Unix socket
            ──→ daemon (0600, same-user socket; daemon never fork/execs claude)

[daemon]
  receives PTY byte stream via the owner Unix socket
  registers an "externally-owned" session
  relays 0x00 frames to /v1/term/<sessionId> WebSocket viewers
  browser contract: output-only, same binary frame format (0x00/0x01)
                    RoleAdmin gate on any future inbound frames
```

The `/v1/term/<sessionId>` endpoint, binary frame format (`0x00`/`0x01`
outbound), auth chain, and `--share-terminal` opt-in flag defined in
the Decision section above are **unchanged**. The daemon's role in
serving browser viewers is unchanged. Only the PTY ownership and the
daemon's exec requirement change.

### Trade-offs vs original T1

**Advantages (why T2-relay wins on hardened hosts):**

- Works where the daemon cannot exec: login shell retains exec
  permission under restrictive seccomp/AppArmor policies that block
  the daemon.
- Native local terminal latency: the login-shell PTY path has no
  additional hop between keystrokes and `claude` — same as `--direct`.
- Daemon needs no exec privilege and no PTY allocation capability.
  Reduces the daemon's required syscall surface.
- `creack/pty` dependency (Required Gate 1) is now owned by the
  `yakos start` binary, not the daemon. The daemon's dependency
  footprint does not grow.

**Costs / new design points:**

- The daemon is now a **relay, not the owner.** The PTY lifecycle is
  bound to the `yakos start` process (login shell), not the daemon.
  If the login shell exits, the PTY session ends; the daemon cannot
  restart or outlive it. This is the T1 "lifecycle inversion" argument,
  now accepted as a necessary trade-off for Phase 1 on hardened hosts.
- **P2 design point — bidirectional browser input.** P2 (browser
  keystrokes → claude) will route inbound frames from browser clients
  back to the **login-shell PTY owner** over the owner socket, rather
  than from the daemon directly into a daemon-owned PTY master. The
  daemon receives `0x10`/`0x11` frames from authenticated browser
  clients and forwards them to the login-shell owner process, which
  writes them to the PTY master. The writer-auth gate (RoleAdmin on
  `0x10`/`0x11` frames) and the security-reviewer pass before P2 ships
  (Required Gate 3) are unchanged and remain mandatory.
- The original T1 "two hops" rejection argument is partially
  reinstated: PTY output now travels login-shell → owner socket →
  daemon → WebSocket → browser (one extra hop compared to T1's
  daemon-direct path). This is accepted; `--share-terminal` is not
  a latency-critical path.

## Amendment (2026-06-18): Phase 2 threat model

**Status:** P2 shipped; independent security review completed. ADR overall
status remains **Accepted**. This subsection records what the review
confirmed and the two items accepted with rationale.

### What Phase 2 is

P2 is bidirectional browser input: a browser client can type into and
resize a shared `claude` session. The session runs `--permission-mode
bypassPermissions`. Any `RoleAdmin` browser that gains inbound-keystroke
access has **operator-equivalent RCE** on the host — the same trust tier
that already holds via `/api/console/bash`. The `RoleAdmin` input gate is
the sole barrier between a `RoleRead` viewer (output-only) and operator
RCE; it must never regress to a lower role.

The terminal endpoints are entirely opt-in (`--share-terminal`). When no
terminal manager exists, the endpoints are unmounted and the attack
surface is zero.

### Confirmed protections (from the independent review)

- **`RoleAdmin` gate is fail-closed and dual-layer.** The outer
  `requireRole` middleware and inner `isAdmin` check must both pass.
  An unresolved identity (missing or invalid credential) receives
  `RoleNone` and is denied before any frame is processed.
- **Inbound frame bounds.** Inbound keystroke/resize frames are bounded
  at two layers: the `x/net/websocket` library cap (64 KB per frame)
  and an owner-payload cap (32 KB). There is no uint16 overflow on the
  resize fields. A `recover()` backstop in the detached goroutine
  prevents a malformed frame from crashing the session.
- **Cross-session isolation.** The browser path reaches only
  externally-owned sessions (registered by `yakos start --share-terminal`);
  it cannot address daemon-owned PTYs or other internal sessions.
  Session IDs are generated with `crypto/rand`.
- **Concurrent same-session writers serialized.** A write mutex on the
  PTY master path serializes concurrent browser writers within one session;
  no interleaving at the PTY layer.
- **Admin input is audit-logged.** Each inbound writer connection is
  logged with session ID and operator identity on connect, providing an
  audit trail for admin-input events.

### Accepted with rationale

**No per-operator session ownership.** Any `RoleAdmin` who knows a
session ID (obtainable via the `RoleAdmin`-gated `/api/term` list) can
drive that session — admin A can type into admin B's session. This is
accepted under the single-/trusted-admin deployment model that P2
targets. If a multi-admin or multi-tenant networked deployment is ever
targeted, per-operator session-ownership binding (associating a session
to the admin identity that created it and restricting input to that
identity) must be added before that deployment is supported. This is a
**known limitation** of the current design.

**RoleAdmin = operator-equivalent RCE (by design).** The trust model
grants `RoleAdmin` the same execution capability as a login-shell
operator. This is not a bug; it is the stated contract. The
`--share-terminal` banner and documentation must make this explicit so
operators can make an informed decision before enabling the flag.

### Cross-reference

The T2-relay topology and the owner Unix socket path described in the
2026-06-18 Amendment above are the foundation P2 builds on: inbound
`0x10`/`0x11` frames travel browser → daemon (writer-auth gate) → owner
Unix socket → login-shell PTY owner → PTY master write → `claude`.
Required Gate 3 (security-reviewer pass before P2 ships) is satisfied by
this review.
