# ADR-0005: Hybrid authentication for the networked console

**Status:** Accepted (operator-approved 2026-06-14)
**Date:** 2026-06-14
**Deciders:** operator — approved the three-regime hybrid auth model and all locked parameters
**Refs:** ADR-0004 (mTLS identity layer — amended by this ADR), `docs/unified-console-plan.md`, `internal/mtls/`, `internal/netid/`

---

## Context

ADR-0004 established mTLS client certificates as the authentication
mechanism for off-loopback networked sessions, and codified a
four-role RBAC model resolved through `netid.Identity`. That decision
holds for machine clients (CLI, CI, API integrations). It left open
the question of how human operators connect from a browser: a browser
cannot natively present a client certificate for a custom CA in a
convenient way, and distributing per-user client certs to browser
users is the unsolved human-factors problem called out in ADR-0004 C2.

The operator now approves a **hybrid authentication model** that
introduces a third auth regime — password + secure session cookie for
networked human operators — while retaining mTLS for machine clients
and the existing loopback bearer token unchanged. The three regimes
must resolve to the same `netid.Identity{OperatorID, Role}` so that
all downstream RBAC, dispatch audit trails, and share-pane ownership
logic remain unchanged.

This ADR amends ADR-0004. It does not replace it: mTLS is retained
as the machine-client regime. The loopback path is unchanged. This
ADR adds the password+session regime and locks implementation
parameters the operator has explicitly approved.

---

## Decisions

### Three coexisting auth regimes, one identity abstraction

| Regime | Clients | Mechanism |
|---|---|---|
| Loopback | Single-host localhost callers | Existing bearer-token `#token=` cooperative labeling — unchanged |
| Networked humans | Browser operators | Password + server-side session cookie over HTTPS |
| Networked machines | CLI, CI, API, future integrations | mTLS client certificates (ADR-0004, retained) |

All three regimes produce the same `netid.Identity{OperatorID, Role}`
value. A session is a third source feeding the existing identity
abstraction; it is not a parallel authorization mechanism.

**Username / CN namespace:** usernames and cert CNs share a single
namespace. Overlap is forbidden at enrollment time. This eliminates
the regime-confusion risk from ambiguous identifiers (operator-chosen
simpler model over per-regime namespacing).

### Resolution precedence in `netid.Resolver`

A single decision point in `netid.Resolver` evaluates regimes in
order and stops at the first match:

1. Verified mTLS client cert → identity from cert CN.
2. Valid session cookie → identity from server-side session store.
3. Loopback-trusted, no credential → today's cooperative bearer-token
   behavior.
4. None of the above → unauthenticated. API paths return 401;
   navigation requests redirect to `/login`. Fail-closed.

### Password authentication

**Hashing:** argon2id with fixed parameters: `time=3, memory=64 MiB,
threads=4, saltLen=16, keyLen=32`. Parameters are PHC-encoded in
storage so they can rise in a future release without a migration.

**User store:** `<stateDir>/users/users.json`, permissions 0600,
parent directory 0700. The file-trust hardening already present in
netid (symlink rejection, world-writable rejection) is reused as-is.

**Lockout:** 10 failed attempts per user triggers a 15-minute cooldown.
A per-IP rate limit applies to `/login`. All authentication paths
execute a constant-time argon2id verify — including for unknown
usernames — to prevent timing-based enumeration. All failure modes
return a generic "invalid username or password"; no distinguishing
error is returned.

### Session management

- Token: 32-byte `crypto/rand`, stored server-side.
- Store: in-memory for v1. Persistence is a flagged follow-on.
- Cookie: `HttpOnly; Secure; SameSite=Strict; Path=/`.
- Idle timeout: 2 hours. Absolute timeout: 12 hours.
- Session ID is regenerated on login and on any privilege change
  (role update, password reset).
- Logout invalidates the session immediately. Disabling a user purges
  all live sessions for that user via a `sessionEpoch` increment.

### CSRF: defense-in-depth

Three layers (operator-chosen):

1. `SameSite=Strict` on the session cookie.
2. The existing JSON-only mutation gate already present in the console
   API (non-JSON `Content-Type` is rejected).
3. Explicit double-submit `X-CSRF-Token` on all cookie-authenticated
   mutations. The Service Worker's role narrows to injecting this
   token on same-origin mutations; it carries no broader auth
   responsibility.

mTLS requests are exempt from the CSRF token requirement: client
certificates are not browser-auto-attached and therefore are not
vulnerable to CSRF.

### First-admin bootstrap

When zero users exist and the daemon is bound off-loopback, only
`/setup` is reachable. All other routes return 403 until the first
admin is created.

A one-time setup token is printed to the daemon's own stdout at
startup. It is single-use, expires in 30 minutes, and is only
accepted when zero users exist and only creates the first admin.
Regeneration: `yakos console bootstrap-token`. This token is never
logged and never transmitted over the network without TLS.

### Admin Users panel and CLI mirror

A Users panel (requires `RoleAdmin`) provides:
create / list / set-role / reset-password / disable / enable / delete.

Self-service password change is available to any authenticated user.
Self-protection: an admin cannot remove the last admin role and cannot
delete their own account while it is the last admin.

CLI mirror: `yakos console user add | list | set-role | reset-password
| disable | enable | delete`.

### RBAC unchanged

The four-role model from ADR-0004 (`read < dispatch < flows-run <
admin`) is unchanged. Enforcement at two points (console edge
middleware + `dispatch.Service` facade) is unchanged.

## Threat model

| Threat | Mitigation |
|---|---|
| Login brute-force | 10-attempt / 15-min lockout per user; per-IP rate limit on `/login` |
| Username enumeration | Constant-time verify for unknown users; generic error message for all failure modes |
| Session hijack via XSS | `HttpOnly` cookie (JS cannot read it); `Content-Security-Policy` on console pages |
| Session hijack via network | `Secure` cookie; HTTPS enforced off-loopback; no plain-HTTP escape hatch |
| Session fixation | Session ID regenerated on login and on privilege change |
| CSRF | `SameSite=Strict` + JSON-only gate + explicit `X-CSRF-Token` double-submit |
| Setup-token theft | Printed to daemon stdout only; 30-min expiry; single-use; zero-users guard; TLS on transit |
| Setup-token replay | Single-use: consumed on first use, then rejected |
| User-store tampering | 0600 file; symlink/world-writable rejection; argon2id hashes resist offline cracking |
| Privilege escalation via stale session | Role resolved from store at each request; session epoch invalidates on disable/role-change |
| Self-lockout | Admin cannot remove last admin role or delete last admin account |
| Regime confusion | Username / CN namespace overlap forbidden at enrollment; `netid.Resolver` stops at first verified match |

## Consequences

**Positive:**

- Human operators can authenticate from a browser without client-cert
  distribution. The ADR-0004 C2 human-factors gap is closed for the
  human regime.
- All downstream RBAC, audit-trail, and share-pane ownership code is
  unchanged — three regimes, one `netid.Identity`.
- mTLS is retained for machine clients; no regression for existing CLI
  and CI consumers.
- The loopback path is entirely unchanged.
- PHC-encoded argon2id parameters allow hardening without a migration.
- Session epoch provides immediate revocation on disable without a
  persistent session store.

**New risks:**

- **C5 — CSRF surface.** The session cookie is a new browser-auto-
  attached credential. The three-layer defense-in-depth (SameSite +
  JSON gate + explicit token) is the chosen mitigation; any weakening
  of any layer must be treated as a security regression.

- **C6 — User store is a credential store.** `users.json` holds
  argon2id hashes. It must be treated with the same care as a secrets
  file. Backup, replication, and log-rotation processes must not
  expose it. World-readable exposure is a credential compromise.

- **C7 — Session state is new operational surface.** The in-memory
  session store is lost on daemon restart (v1 behavior, documented).
  Users are logged out on restart. Persistence is a follow-on; until
  it lands, operators must document the restart behavior.

- **C8 — Two role stores.** Roles are carried in `users.json` (for
  the password regime) and implicitly in the cert CN / CA trust
  (for the mTLS regime). These must be kept consistent; a role
  change in `users.json` does not affect an existing mTLS client's
  cert, and vice versa. The `netid.Resolver` reads the current store
  on each request, so `users.json` changes take effect immediately.
  mTLS role changes require cert reissuance.

- **C9 — Username / CN namespace collision handling.** The chosen
  model (forbid overlap at enrollment) is simpler than per-regime
  namespacing but requires enforcement at every enrollment path
  (user create, cert issuance). Missing this check at any path
  creates an identity-confusion vulnerability.

**Phased rollout (high level):**

Implementation proceeds in seven phases: (1) `netid.Resolver`
abstraction and three-regime wiring; (2) user store + argon2id;
(3) login/logout HTTP handlers + session middleware; (4) CSRF
defense-in-depth; (5) bootstrap flow + `/setup`; (6) Admin Users
panel + CLI mirror; (7) integration tests covering all three regimes
and the RBAC matrix. No networked auth code ships before the gates
below are satisfied.

**Required gates before networked auth code ships:**

1. Operator (human) approval of this ADR. (✓ — approved 2026-06-14)
2. Security-reviewer pass on the implementation PR covering CSRF
   surface, session lifecycle, and bootstrap flow (per
   `rule:pr-conventions`).
3. Red-team pass on `/login`, `/setup`, user-disable revocation, and
   regime-confusion paths.
4. Automated tests covering all three auth regimes, the full RBAC
   matrix, and the `netid.Resolver` precedence order.

## Alternatives considered

**Per-user bearer tokens for human operators.**
Replayable; no binding to the transport layer; requires a distribution
and revocation store. Kept for CI/headless machine clients behind a
trusted reverse proxy (existing behavior); rejected as the primary
human-operator mechanism.

**OIDC/SSO for human operators.**
Imports an external IdP dependency. Disproportionate operational
complexity for the target operator count. Explicitly rejected;
revisit if the operator headcount grows to the point where a
centralized directory is warranted (same rationale as ADR-0004).

**Client-cert distribution tooling for browser users (extend ADR-0004
rather than add a new regime).**
Browser UX for custom-CA client certs is poor across all major
browsers. Solving the human-factors problem (ADR-0004 C2) by improving
cert distribution tooling defers the UX problem rather than solving
it. A password+session regime is the standard solution for this class
of user and is the chosen approach.

**Per-regime namespacing for usernames and cert CNs.**
Avoids enrollment-time collision checks but allows the same string
(`alice`) to resolve to different identities depending on which regime
authenticated the request. Operator-chosen to forbid overlap instead:
simpler reasoning, explicit enforcement point, no silent identity
ambiguity.
