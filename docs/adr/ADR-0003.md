# ADR-0003: Headless Flows DAG engine (Phase 4)

**Status:** Accepted
**Date:** 2026-06-12
**Deciders:** yakOS backend specialist (Phase-4 Flows engine)
**Refs:** `docs/unified-console-plan.md` §Phase 4, `internal/workflow/`

---

## Context

yakOS needs a DAG executor for multi-agent workflow "Flows" (see
`unified-console-plan.md` §Phase 4). A Flow is a directed acyclic
graph of agent dispatch nodes where outputs from upstream nodes are
threaded into downstream node prompts.

Requirements driving this ADR:

1. Dispatch each node through `dispatch.Service` (governed + identity-
   stamped) — never bypass the global concurrency governor.
2. Support parallel execution of independent nodes within a run.
3. Persist run state so daemon crashes do not lose progress.
4. Allow resume from a partially-completed run after a node failure.
5. Prevent resume against an edited workflow graph (undefined semantics).
6. Cap prompt inflation from upstream outputs (prevent OOM from large
   LLM outputs substituted into downstream prompts).

---

## Decisions

### Run ownership: self-asserted `operator_id`

Each run carries an `owner_operator_id` stamped onto every node
dispatch via `dispatch.Params.OperatorID`. This attribute is
**self-asserted** by the caller (cooperative labeling for uid-equivalent
teammates on the same host). It is used for audit-trail attribution in
the dispatch log only. It is NOT an authorization boundary: all
operators on the same loopback daemon are uid-equivalent and have equal
access to run, resume, and inspect any workflow.

This matches the Phase 2 identity model documented in the
`unified-console-plan.md` §Multi-user scope decision.

### Concurrency model: Kahn topo-sort + per-run semaphore under the global governor

The engine uses Kahn's algorithm to maintain a ready-set (nodes whose
in-degree is zero). Nodes in the ready-set are launched concurrently
under a per-run `max_parallel` semaphore (default 4 slots). This
semaphore sits INSIDE the global `dispatch.Service` governor (default
8 slots across all transports). Effective concurrency is therefore
`min(max_parallel, governor_cap - in_flight_from_other_transports)`.

**Sub-dispatch nesting hazard:** a workflow node that re-enters the
daemon via any transport (gRPC/REST/JSON-RPC/MCP) competes for the
same governor slots as its parent workflow run. A workflow with 4
parallel nodes at max_parallel=4 and governor_cap=8 leaves 4 slots
for nested dispatches. Deep nesting (workflow → node → node dispatches
own sub-flows) can exhaust the cap and stall. The nesting hazard is
documented and deferred; the recommended mitigation is raising
`MaxConcurrent` in `ServiceConfig` if deep nesting is observed.

### Failure semantics: fail-fast propagation, independent branches complete

When a node fails (Go error OR `Result.ExitCode != 0`):

1. The node is marked `failed`.
2. All transitive dependents are marked `skipped` (via `failedSet`
   propagation in the scheduler).
3. Independent branches that are already running or ready continue to
   completion.
4. The run is marked `failed` when the graph drains.

Non-zero exit code is checked **separately** from the Go error return,
matching the dispatch contract (`Result.ExitCode != 0` is not a Go
error — `dispatch.Run` returns nil error on non-zero exit).

### Resume-from-failure: skip completed, re-run failed/skipped

`Engine.Resume` loads the prior run's `run.json`, identifies nodes in
`completed` state, and reuses their pinned outputs. Nodes in `failed`
or `skipped` state are re-run in the new run.

**Output pinning on resume:** completed nodes' stdout files
(`runs/<priorRunID>/nodes/<id>.stdout`) are copied into the new run
directory verbatim. The **same upstream output** is threaded into
downstream prompts — not a re-roll. This is intentional:
re-dispatching completed nodes for a "fresh" output would make resume
non-deterministic and waste tokens on already-expensive nodes.

**M1 — pinned output integrity (same-uid trust):** the `nodes/<id>.stdout`
files are NOT integrity-protected at the cryptographic level. They are
stored on the same filesystem as the daemon and trusted by same-uid
access control only. A compromised file cannot cause path traversal
(all node IDs are validated against `^[a-z0-9][a-z0-9-]{0,63}$`
before any path construction — see C2 guard in `runstate.go:stdoutPath`),
but a tampered output would be silently used on resume. Operators
requiring tamper-evidence may record a per-output SHA-256 digest in
`run.json` and verify on resume-seed; this is not implemented in the
current version (deferred — file modification by same-uid process is
outside the threat model for a loopback daemon).

### Resume forks a new runID with `parent_run_id`

Resume does NOT mutate the prior run. It creates a new run with a
new `runID` and records `parent_run_id` pointing at the original.
This preserves the audit trail: both the original partial run and the
resumed run are independently inspectable. The dispatch log entries
from the resumed run carry the new `runID` as the session context.

### YAML-hash pin: reject resume against an edited graph

At the start of each run, the engine computes a SHA-256 of the
serialised workflow YAML and records it in `run.json` as
`workflow_hash`. On `Resume`, the current workflow's hash is computed
and compared against the recorded hash. If they differ, Resume fails
loudly with an explicit error.

**Rationale:** resuming against an edited graph is undefined. If a node
was renamed or re-wired between the original run and the resume attempt,
the pinned output from the old node has no safe mapping to the new
graph. The operator must start a new run if the graph has changed.

### `output_limit` as total tail-truncate budget per downstream node

Each node declares a MANDATORY `output_limit` (bytes). This is the
**total budget** for all upstream node outputs substituted into that
node's prompt. If the sum of upstream outputs exceeds `output_limit`,
the engine tail-truncates proportionally (each upstream output is
allocated a fraction of the budget proportional to its share of the
total upstream bytes). Truncation emits a `workflow.node.truncated`
bus event carrying only byte counts (not content).

`output_limit` is mandatory (validate rejects a missing or zero value)
because unbounded upstream output substitution is a prompt-injection
amplification vector and can exceed LLM context windows silently.

### Crash/restart reconciliation

On daemon startup, `workflow.ReconcileInterrupted(runsDir)` scans
`runs/*/run.json` for runs left in `running` state (indicating a hard
kill mid-run) and marks them `interrupted`. Nodes left in `running`
state within those runs are marked `failed` with the message "daemon
interrupted (crash reconciliation)".

**Detected limit:** reconciliation operates at the `run.json` level
only. It does NOT scan the dispatch NDJSON log for orphaned
`dispatch_started` entries without a matching `dispatch_finished`. This
detection would require correlating NDJSON entries with node IDs and
run IDs, which is non-trivial given that the dispatch log is keyed by
agent/project/timestamp rather than workflow run context. This
detection is deferred.

The implication: after a crash, a node marked `interrupted/failed` may
have actually completed its subprocess (SIGKILL only fires when the
daemon process context is cancelled; subprocesses can outlive the
daemon). The operator should inspect the node's partial output in
`runs/<runID>/nodes/<id>.stdout` before resuming. Resume-from-failure
handles this correctly: the re-run of a previously-completed-but-not-
recorded node is idempotent from the dispatch system's perspective
(the agent is dispatched again; the cost is paid again).

### Bus events: lifecycle metadata only, no content

Five new `workflow.*` topics are added to `wsbus/event.go`:

| Topic | Payload |
|---|---|
| `workflow.run.started` | `run_id`, `workflow`, `ts` |
| `workflow.run.finished` | `run_id`, `workflow`, `status`, `ts` |
| `workflow.node.started` | `run_id`, `workflow`, `node_id`, `agent`, `ts` |
| `workflow.node.finished` | `run_id`, `workflow`, `node_id`, `status`, `exit_code`, `ts` |
| `workflow.node.truncated` | `run_id`, `workflow`, `node_id`, `original_len`, `truncated_to`, `ts` |

**Invariant (enforced by `TestBusInvariant_NoContentPayloads`):** no
node output, prompt content, or token is published on the bus. The bus
carries only lifecycle metadata. This invariant is tested by the
exhaustive topic registry gate in `internal/wsbus/server_test.go`.

### Persistence: debounced atomic writes

`RunState` is written to `runs/<runID>/run.json` via a background
goroutine that flushes every ~200ms (debounced). Per-node stdout is
stored in `runs/<runID>/nodes/<id>.stdout` to keep `run.json` small.
Both writes use the atomic temp-file + rename pattern from `kanban/write.go`.
`stopDebounce()` is synchronous: it closes the stop channel and waits
for the goroutine to complete its final flush, so `Run` does not return
until the final state is durably on disk.

## Consequences

**Positive:**

- Node dispatches inherit cost/perf/finops attribution automatically
  (they flow through `dispatch.Service`).
- The global concurrency governor bounds workflow + direct dispatch
  concurrency together — no separate throttle to tune.
- Resume-from-failure is safe to use after daemon crashes, node
  timeouts, or infrastructure errors affecting only some nodes.
- The YAML-hash pin makes the resume contract explicit and verifiable
  rather than silently undefined.
- The bus invariant (no content on events) keeps the 1000-event replay
  ring available for lifecycle events rather than flooding it with
  large node outputs.

**Negative / tradeoffs:**

- Output pinning on resume means a downstream node always sees the
  same upstream output on retry, even if the upstream's "correct"
  output might differ on a fresh run. This is the intended semantics
  (expensive partial state is preserved) but means a corrupted upstream
  output requires starting a new run from scratch rather than retrying
  the upstream.
- The YAML-hash pin rejects any resume after even a whitespace-only
  edit to the YAML file. Operators must be aware that editing a
  workflow mid-run invalidates outstanding resumes.
- The proportional truncation strategy distributes the `output_limit`
  budget across upstream outputs by byte-share. A single very large
  upstream output will consume most of the budget, leaving little for
  smaller ones. A per-source limit option is a future extension.
- Orphaned subprocess detection after daemon crash is not implemented.
  The cost of a re-run is accepted as the recovery mechanism.

**Deferred:**

- Per-run `max_parallel` is a compile-time constant (4); making it
  a per-workflow YAML field is a minor extension deferred to Phase 5.
- Orphaned `dispatch_started`/`dispatch_finished` NDJSON reconciliation
  (requires log-to-runID correlation key).
- Phase 5 UI: live canvas + YAML-first authoring surface in the console
  under `/flows/*`, subscribing to `workflow.*` bus events.
