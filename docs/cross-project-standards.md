# Cross-project standards

Operator-facing guide to the six standards yakOS injects into
every project that opts in. Sister document to the per-standard
rules (`lib/rules/*-discipline.md`) and skills
(`lib/skills/*-scaffold/SKILL.md`).

**Last updated:** 2026-05-22 (Plan 4 M4 ship at v0.22.0.0).

---

## What this is

Cross-project standards are conventions yakOS encourages every
project it manages to ship: structured logs, a UI changelog, a
process supervisor, a feedback loop, an architecture page, and
a clear about page for new users.

Each standard is **opt-in per project** via `.yakos.yml`. yakOS
doesn't push opinions onto projects that don't want them. When
a project opts in, three layers fire:

1. **Soft control** — a rule (`lib/rules/<standard>-discipline.md`)
   loaded into the lead's context. Guides the agent's behavior.
2. **Scaffold** — a skill (`lib/skills/<standard>-scaffold/SKILL.md`)
   the operator invokes once per project. Drops in working
   starter code.
3. **Hard control** — an audit-time check appended to the
   relevant release-audit playbook
   (`lib/playbooks/02-code-quality.md`,
   `lib/playbooks/04-docs-architecture.md`, or
   `lib/playbooks/08-infra-deploy-deps.md`). Catches drift.

The three layers compose: the rule teaches; the scaffold seeds;
the audit catches.

## Project profile types

`.yakos.yml`'s `profile.type` field tags the project. The type
drives which standards yakOS suggests by default. Operator
overrides freely via `profile.standards.<name>: true|false`.

| Type | Default-true standards |
|---|---|
| `web-app` | logging, changelog-ui, monitors, feedback, architecture-viz, about-page |
| `service` | logging, monitors, architecture-viz |
| `library` | architecture-viz, about-page |
| `cli-tool` | logging, about-page |
| `data-pipeline` | logging, monitors |

The defaults are starting points — operators tighten or loosen
as the project's actual shape becomes clear.

## `.yakos.yml` profile schema

Lives at the project repo root. Generated by `yakos init`. Edit
freely.

```yaml
yakos: 0.9

profile:
  type: web-app
  standards:
    logging: true
    changelog-ui: true
    monitors: true
    feedback: false           # not all projects need user feedback
    architecture-viz: true
    about-page: true

  # Per-standard config overrides (optional; defaults are sensible).
  logging:
    format: json              # json | text | logfmt
    levels: [debug, info, warn, error]
  monitors:
    targets: [api, worker]
  changelog-ui:
    component_path: web/src/components/Changelog.tsx
```

The `_doc` key (legal in the template) is operator-readable and
ignored by yakOS parsers.

## CLI surface

`yakos standards` covers all opt-in management:

```sh
yakos standards list                # show all 6 standards + state
yakos standards enable  <name>      # opt in
yakos standards disable <name>      # opt out
yakos standards check               # preview what active standards catch
yakos standards init                # interactive profile + standards selection
```

`<name>` is one of:
`logging | changelog-ui | monitors | feedback | architecture-viz | about-page`.

### Typical first-time flow

```sh
# 1. Bootstrap a project (creates .yakos.yml template).
yakos init myproject --project ~/code/myproject

# 2. Interactively pick profile type + suggested standards.
cd ~/code/myproject
yakos standards init

# 3. Verify the result.
yakos standards list

# 4. Run the per-standard scaffolds to drop in starter code.
#    (Each scaffold detects the project's backend/frontend stack.)
yakos dispatch frontend "run skill:logging-scaffold"
yakos dispatch frontend "run skill:about-page-scaffold"
# ...etc per active standard

# 5. Preview what release-audit will catch.
yakos standards check
```

### Common adjustments

```sh
# Change project type (e.g., started as web-app, became library):
yakos standards init                 # walks through it
# OR edit profile.type directly in .yakos.yml.

# Opt in to a specific standard the type didn't suggest:
yakos standards enable feedback

# Opt out of a noisy standard:
yakos standards disable monitors
```

## How standards compose with release-audit

When the lead invokes `release-audit` (the multi-domain audit
that yakOS ships at `lib/skills/release-audit/SKILL.md`), each
domain playbook is read. The §-prefixed sections check
profile-gated standards:

- `02-code-quality.md` audits Standard 1 (logging) and Standard
  4 (feedback) when active
- `04-docs-architecture.md` audits Standard 2 (changelog UI),
  Standard 5 (architecture viz), and Standard 6 (about page)
  when active
- `08-infra-deploy-deps.md` audits Standard 3 (monitors) when
  active

Active = `profile.standards.<name>: true` in `.yakos.yml`.
Disabled standards' checks don't fire — release-audit stays
focused on what the project committed to.

### Severity scale (per-standard variations)

Each playbook section documents exact severities for its
detections. Common patterns:

- **P0** — security (logs containing secrets; auth bypass)
- **P1** — broken contract (missing API endpoint required by
  a committed standard; cite-without-data orphan)
- **P2** — quality / drift (no-op healthcheck; stale diagrams;
  excessive `console.log` count)
- **P3** — polish / hygiene (missing runbook; placeholder
  text; resolved-without-citation)

## Per-standard quick reference

### Standard 1 — Logging

- **What:** structured logs across services
- **Required:** `ts`, `level`, `component`, `message`, `trace_id`
- **Forbidden:** `print` / `console.log` / `println!` in
  production; secrets in log messages
- **Scaffold:** per-language logger module (Go/Node/Python/Rust)
- **Common gotcha:** existing custom logger — scaffold detects
  and warns; operator decides migration

### Standard 2 — Changelog UI

- **What:** project version + changelog visible in the UI
- **Required:** single `CHANGELOG.md` source (the same one
  `pre-push-version-gate.sh` enforces); version display
  matches `VERSION` file
- **Forbidden:** parallel changelog artifacts; hard-coded
  version strings
- **Scaffold:** per-frontend page route + version badge +
  build-time `CHANGELOG.md` import
- **Common gotcha:** Vite needs `?raw` import; Next.js may
  need MDX or runtime fetch

### Standard 3 — Monitors

- **What:** every long-running service has supervisor +
  `/healthz` + restart runbook
- **Required:** supervisor config (systemd / pm2 / k8s /
  docker-compose); real liveness check (DB ping, downstream
  reachability); documented restart procedure
- **Forbidden:** `/healthz` that always returns 200
  (no real check); services in `profile.monitors.targets`
  without a supervisor entry
- **Scaffold:** per-supervisor configs + `/healthz` stub +
  runbook skeleton per service
- **Common gotcha:** initial-delay tuning for slow-starting
  services; restart-loop hiding root cause

### Standard 4 — Feedback

- **What:** user submits feedback; admin triages; changelog
  cites resolved items
- **Required:** `feedback` table + submit/list/update API +
  submit widget + view-my-feedback page + `Feedback #<8hex>`
  citation pattern
- **Forbidden:** drop-table on rollback (use rename-to-archive);
  feedback IDs visible to users that aren't UUIDs; cite-without-
  data orphans in CHANGELOG.md
- **Scaffold:** DB migration + API + UI per stack
- **Common gotcha:** screenshot storage left unwired (TODO);
  admin role middleware must exist or be stubbed; 8-hex
  prefix collisions at scale (~64k records)
- **Auto-deselects** for `library`, `cli-tool`, `data-pipeline`
  profile types

### Standard 5 — Architecture viz

- **What:** static page rendering ADRs + Mermaid diagrams +
  CHANGELOG timeline + SBOM + tech-debt + novel-capabilities
- **Required:** `docs/architecture/*.mmd`, `docs/adr/*.md`,
  `docs/tech-debt.md`, `docs/novel-capabilities.md`, a
  rendered architecture page
- **Forbidden:** PNG-only diagrams (rot guaranteed); ADRs
  without `Status:` declaration
- **Scaffold:** per-framework page renderer + skeleton source
  files + Mermaid → SVG build pipeline
- **Common gotcha:** Mermaid CLI requires Node; SBOM section
  is collapsed by default; `architect.md` agent owns the
  ongoing maintenance discipline

### Standard 6 — About page

- **What:** 3-paragraph "what is this?" page for first-time users
- **Required:** route exists; three paragraphs filled in (no
  placeholder TODOs)
- **Forbidden:** marketing copy; feature lists; team-page
  content; auto-generated from README
- **Scaffold:** per-frontend route + template + version
  badge
- **Common gotcha:** stale (>90 days) while project ships
  actively — audit P3

## Composition between standards

Several standards compose naturally:

- **About page + architecture viz** — operator may merge them
  into one `/architecture` page with about as the hero (use
  `--include-about` on `architecture-viz-scaffold` or
  `--merge-into-arch` on `about-page-scaffold`)
- **Changelog UI + feedback** — citation handles in the
  changelog UI link to feedback records when both are active
- **Architecture viz + retrospectives** — when the framework's
  retrospective milestone (Plan 3 M1) is active, the
  architecture page reads `decisions.md` history into a
  timeline panel
- **Monitors + observability tools** — yakOS scaffolds the
  artifacts (configs, healthcheck endpoints); shipping logs +
  metrics + traces to a cloud observability stack is downstream
  ops work

## What this doc deliberately does NOT cover

- Per-language framework specifics (those live in each skill's
  SKILL.md)
- Deploy infra integrations (k8s / Heroku / Vercel templates)
- Real-time observability dashboards
- Auto-detection of technical debt (operator maintains
  `docs/tech-debt.md` manually)
- Marketing / positioning copy for the about page (operator
  writes it)
