## Architectural gaps surfaced during cold-read familiarization

### G1 — Lead supervision has no hard counterpart

Surfaced by: the v0.1.1 cold-read familiarization session
(`work/current/decisions.md` from that session, watch area "(b)").

The framework's `lead-template` agent body says (verbatim):

> **Don't do specialist work yourself.** If a teammate can do it,
> dispatch. Lead context is for coordination; specialist context
> is for execution.

This is a soft control. There is no hard counterpart. A lead that
quietly does specialist work doesn't trip any hook. The hard/soft
taxonomy in PHILOSOPHY.md says "when in doubt, pair a soft control
with a hard one" — this is one of the few cases where that's not
done.

Why it matters: lead-doing-specialist-work is a primary failure
mode for team coherence. It's invisible until late (the audit trail
shows the lead's edits look like normal work; only the *pattern*
across a session reveals the issue).

Possible v0.2 mechanism: a `SessionEnd`-time check that compares
lead-vs-teammate edit counts and warns if the lead did >N% of the
file-touches itself (heuristic; tunable per project). The check
would live in `session-end-check.sh`'s audit pass and surface as
WARN, not block. Calibration N would need real-use data — too
strict and small projects warn constantly; too lax and the failure
mode it's catching slips through.

### G2 — `yakos validate` doesn't detect documentation drift

Surfaced by: the v0.1.1 cold-read familiarization session (watch
area "(c)") — and immediately demonstrated by the same session
finding 4 stale "lib/playbooks/ is empty" claims in v0.1.1 docs
that Batch 5.7 had silently invalidated.

Why it matters: documentation drift is a cumulative failure mode.
Every batch that renames a thing or fills a gap creates potential
drift; every doc that quotes the old state ages out. Without a
detector, drift accumulates until a fresh reader stumbles on it.

Possible v0.2 mechanism: a `yakos validate --docs` mode that
greps known files for stale-phrase patterns. Examples:

- `lib/playbooks/.*empty` (now wrong since v0.1.1)
- `Batch.*not yet implemented` (caught the v0.1.0 → v0.1.1 fix)
- `06-hipaa-phi` (now `06-regulated-data`)

The grep targets become a maintained list. False positives are
acceptable (this is a doc check, not a code gate); false negatives
are the real cost. Pair with a "claim-vs-reality" check: every
"v0.X populates Y" or "Y is empty in v0.1" claim has its
truth-value re-verified at validate time.

A simpler shape: a list of known-stale-phrases under
`tests/doc-drift-patterns.txt`, one per line, treated as ripgrep
patterns. Validate fails (or WARNs) if any pattern matches a
markdown file. Update the pattern list when you fix drift; the
next batch's drift is caught at validate time.

### G3 — Inventory counts include INDEX.md / README.md

Surfaced by: the v0.1.0 build itself (every batch's status report
flagged the count was off-by-one for rules; same logic applies
to skills/agents whenever an index/readme exists in the same
directory).

Trivial fix: `count_dir_files()` in `cli/lib/validate.sh` excludes
`.gitkeep` and `README.md` already; add `INDEX.md`. Cosmetic but
visible on every `yakos validate` run.

## v0.2 agent roster (per docs/team-shapes.md)

**Stack-specialist templates landed in v0.1.4** (`backend`, `frontend`,
`mobile`, `database`, `maintainer`) — derived from generalizing
PandaOS's project agents. Those templates **complement** this roster;
they fill in stack-shaped specialists (server-side, web UI, mobile,
relational DB, housekeeping). The v0.2 roster below covers the
**cross-cutting roles** that aren't stack-shaped.

Order of priority by frequency-of-need:

1. `architect` — every greenfield project needs one
2. `incident-responder` — every project in production
3. `release-manager` — projects past their first release
4. `devops-infra` — projects with non-trivial deploy infra
5. `log-analyst` — projects with significant production logs
6. `performance-engineer` — projects under perf scrutiny
7. `privacy-reviewer` — projects with regulatory exposure
8. `accessibility-reviewer` / `ux-reviewer` — user-facing projects

Each agent shipping needs:

- The agent file in `lib/agents/<name>.md` (80–140 lines, five
  specialist questions).
- A corresponding playbook in `lib/playbooks/` (when the agent
  has a domain playbook).
- A team-shapes entry in `docs/team-shapes.md` updated from
  "(NEW — needed)" to a real reference.
- A CHANGELOG entry.

Don't add agents speculatively. Wait for concrete demand.
