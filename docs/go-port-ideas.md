# yakOS Go-port rebuild-ideas wishlist

## Purpose + how to use

This is the running wishlist of "while we're rewriting anyway" ideas for the Go port. The bar to land on the list is low — capture anything that *might* be load-bearing during the rewrite window. The bar to actually ship is high: each idea is ranked by `value × (marginal-cost-now − marginal-cost-later)`. Things cheap-now-but-expensive-later (schema versioning, observability hooks, error-message ergonomics baked into command dispatch) bubble up; things equally costly now or later (TUI, WASM target) sink. Add ideas via the process at the bottom. The plan itself lives in `docs/go-port-plan.md`; this doc does not duplicate it, it adds to it.

## Top-3 deep dive

**Rank 1 — Schema versioning + migration framework.** Every byte the Go port writes to `kanban.md`, `dispatch-log.ndjson`, `settings.json`, or any new file becomes an implicit v1 contract the moment shadow mode users start storing it. The plan already commits to byte-identical writes (parity contract in §3, decision #13 atomic-write, rank 7 round-trip tests), which is the *interop* shape — but interop is not versioning. If we ever need to add a field to a kanban line or rotate dispatch-log JSONL keys, no migration framework means writing one-off detection heuristics for each format, each time. Stamping a `schema_version:` header (or a sidecar `.schema-version` file for formats where a header would break parity) plus a `yakos migrate-schema` subcommand costs ~8h during bootstrap. The same retrofit at Phase 3 would touch every reader/writer in the codebase and require backfilling versions onto already-deployed files. Highest value × lowest marginal cost on the board.

**Rank 2 — "Did you mean?" + `yakos help <topic>` with examples.** The dispatcher is greenfield (Decision #3, stdlib `flag` + manual subcommand dispatch). Adding a Levenshtein-distance check for unknown subcommands and a help-topic registry that subcommands can register entries into is a one-time ~4h addition at dispatcher-write time. The same feature added in Phase 2 means touching every subcommand registration. The user-visible win is real: bash `yakos` today silently exits 64 on `yakos kanbn`, which is a top-of-funnel onboarding stumble.

**Rank 3 — Capability advertisement.** `yakos capabilities --json` returns the installed runtimes, supported subcommands, schema versions, daemon presence/absence, and hook variants. Phase 2's daemon, MCP server, IDE extensions, and the existing `runtime-pick` skill all need this surface. `doctor` (rank 5) already probes the runtime presence; capability advertisement is a structured wrapper around that probe. Building it at `doctor`-port time costs ~6h; building it later means rewriting `doctor`'s output to be machine-consumable, then adding the wrapper anyway.

## Bottom-3 / "explicitly defer or reject"

**Rank 22 — WebAssembly target.** A WASM build constrains every dependency choice for the lifetime of the project: no syscalls, no CGo (already a non-goal, Decision #9, but WASM adds more constraints), no file-system writes in browser variants. There is zero operator demand signal. The opportunity cost — preserving the freedom to pick the *best* Go library for any given subsystem — is permanent. Reject until at least three operators ask for it in writing.

**Rank 21 — Multi-agent transaction model.** "Atomicity for dispatch A then B then C" sounds desirable until you specify it. What happens when B's runtime crashes mid-token? Rollback the file edits A made? Roll forward and skip B? The semantics fork in ways that need a real operator use case to disambiguate, and the cost of building a wrong abstraction is high (every dispatch path gains a transaction boundary). The existing `peer` + sequential dispatch + `iterate-until` skill cover the common cases. Defer until a concrete use case appears that the existing primitives genuinely can't express.

**Rank 20 — Multi-host coordination.** Cross-machine dispatch implies an auth model (mTLS? shared token? OIDC?), a discovery protocol (mDNS? configured registry?), and a network-failure semantics (split-brain on kanban edits?). All of those are Phase 4+ design discussions the team hasn't had. The plan's Phase 2 WebSocket multi-dev coordination is enough for the near-term "multiple devs on one machine" case. Park multi-host until single-host multi-dev has been in operator hands six months and someone *asks* for the next step.

## How to add an idea to this doc

1. Edit this file directly (this doc is the lead's wishlist; specialists don't write to it).
2. Add a row to the ranked table. Provisional rank is fine — sort later.
3. Fill all five columns. If you can't write the "why now, not later" sentence, the idea isn't ready; park it in your personal notes until you can.
4. If the idea overlaps the plan, mark "Already in plan? Phase X" and link the row to that section. Do not duplicate plan content here.
5. If the idea displaces an existing top-3 or bottom-3 entry, rewrite that deep-dive paragraph in the same PR. Don't leave stale prose.
6. Re-sort the table on every edit. The ranking is the load-bearing part; an unsorted list is a slack channel, not a wishlist.
7. Ideas that survive 3 ranking passes without bubbling above rank 15 are candidates for outright removal — propose deletion with a one-line rationale in the PR description.
